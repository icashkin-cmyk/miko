# dghp-travel v0.4｜旅遊行程規劃（Claude 版，可執行）｜2026-10-30
來源：Codex Skill dghp-travel-field-manual 1.1.0-CANDIDATE（治理整包快照）＋綜合區專案指令 §5–6＋MIKO 2026-10 指示。本 Skill 是 Claude 端精簡 Candidate，不宣稱等同原件；原件沒有、由 Claude 端加上的整合項標「（Claude 端整合）」。
載入順序：先 miko-core（四視角主流程、品質閘門），再本 Skill；以下依 miko-core §2.4 提供四段內容。v0.2 依 2026-10-26 實跑結果改寫（ADR-015）。

## 0. 分流（先做）
- 純旅遊／排行程 → 本 Skill。純找吃的、單店研究 → 停止，改用 dghp-food。旅遊＋美食 → 本 Skill 主導，餐飲節點交 dghp-food。需求含糊（只說要去哪、沒說要吃還是要玩）時依意圖問一句，不強制轉美食。（2026-10-30，H-06）
- 既有行程只換一餐 → 只重算該餐飲節點與前後路線、時間、成本，其他節點凍結；只有造成固定班次、最後入場、返程或重大預算的硬衝突才最小擴張。
- 有地名、位置或距離不等於要排行程。明顯是找吃的（提到餐點、餐廳、吃）→ FOOD；意圖看不出來 → 依上一條問一句，不預設為 FOOD。

## 1. 問問題
- 必問（缺了才問，一次問完）：日期、起點、目的地或想去的點、最晚回到家的時間。
- 預設（沒說就用，並寫出採用的預設）：交通依使用者設定的交通方式（各種方式分開判斷，不預設使用者會開車或騎機車）；起點只給區名時用區公所當起點並標註；預算不限；寵物不同行。（Claude 端整合）
- 對齊需求（原件 TR00、TR03）：時間、地點、交通方式、預算，以及使用者指定的硬性時間；寵物是否同行依原件 §10。

## 2. 解決（可執行步驟）
規劃順序：起點與終點 → 主要交通 → 目的地樞紐 → 地理分群 → 景點／餐飲／休息 → 返程 → 終點。禁止無意義折返。
1. 天氣（Claude 端整合：查詢時用 tw-alert-check）：T-7 看趨勢、T-24H 正式重驗、T-3H 當日重驗；體感 >32°C 啟用高溫路線，降雨機率 >60% 啟用雨天檢查；官方警報或封閉優先。32°C、60% 是規劃用的啟發值，不是官方危險標準；危險判斷依官方警報（tw-alert-check）。T-24H、T-3H 是做行程時的重驗點，不會自動新增排程。中央氣象署縣市頁是動態頁，網頁讀取工具可能讀不到數據（2026-10-26 實跑讀不到）：讀不到就標 NOT_RETRIEVED，附官方連結，判定最多到 NEEDS_FINAL_CHECK。
2. 地點與營業：用 Google 地點搜尋（places_search）查每個點的地址、座標、每週營業時間；以目標日期的星期與預計抵達時間判斷常態開放與最後入場。週表不等於指定日一定開放：特別休館、臨時公告、最後入場或最後點餐要另查官方網站或官方社群公告，結果寫成「指定日狀態」；沒核到就標 UNKNOWN，該點會讓整體判定停在 NEEDS_FINAL_CHECK。
   - 名稱相近或分館要核對地址（實跑：查某景點的分館，回傳的是另一館，指定分館本體沒出現）；地址對不上就標 ENTITY_CONFLICT，不當已核實。
3. 交通：班次必須對應目標日期；他日或一般時刻只能標 PROVISIONAL。官方來源優先（台鐵、高鐵、交通部 TDX；取得方式依當下工具實測，讀不到標 NOT_RETRIEVED，班次與票價一律不得生成）。固定班次、預約、最後入場建立 HARD_CUTOFF。不同交通方式要分開計算，並計入去程＋當地＋返程＋安全餘裕。
   - 騎車或步行時間：沒有導航工具時，用座標以程式算直線距離乘 1.3 估路程，再除以速度（使用者常用交通工具約 15 公里／小時（設定值）、步行約 4.5 公里／小時），一律標「估算，非導航」，判定最多到 NEEDS_FINAL_CHECK。（Claude 端整合）
4. 餐飲節點：交 dghp-food，順序是實體核驗 → 品質 → 路線適配 → 插入行程。本 Skill 只判斷路線、時間、距離、排隊、預算與閉環適配，不改寫 FOOD 的品質結論。
5. 住宿（多日）：依當天最後一站與隔天第一站選區。
6. 時間軸：每個節點寫抵達、停留、離開；最後一段必須回到起點，並和最晚回家時間比，留安全餘裕。
7. 備案：用「條件 → 動作」寫，必須接回閉環；備用班次也要已核實。
8. 呈現：用行程卡或地圖（itinerary_display、places_map_display）加文字；格式見 §5。地圖與行程卡只是呈現，不是核驗；平台沒有同名工具時改用文字表格，核驗與判定照常。

## 3. 後設（常見錯誤）
狀態不可混用：路線已規劃≠可執行；查到時刻表≠指定日期班次已核實；Google 找到實體≠本輪已取得 Google 資料核實；現在營業≠抵達時營業；找到旅館≠有空房；Google 星等≠目前餐飲品質；UNKNOWN≠PASS，成本 UNKNOWN 不得填 0。
- 景點：以目標日期與預計抵達時間判斷開放與最後入場。
- 分館、同名地點選錯；估算的騎車時間被當成導航時間；週末與平日營業時間不同。

## 4. 檢查（驗收）
執行判定：交通指定日、返程、餐飲實體與抵達時營業、天氣、過夜住宿依適用性逐項驗。有 UNKNOWN → NEEDS_FINAL_CHECK；已知關鍵失敗或沒有返程 → DO_NOT_EXECUTE；必要項全部成立才是 READY_TO_GO。READY_TO_GO 只代表截至核驗時間的評估，要寫出核驗時間；出發前狀態有變就重驗。規格與呈現通過不等於旅程可執行。
- AC-T1：時間軸閉環回到起點，且早於最晚回家時間。
- AC-T2：每個點都有週表判斷與指定日狀態（特別休館、臨時公告、最後入場或點餐；沒核到標 UNKNOWN）。
- AC-T3：天氣、班次標出官方來源或 NOT_RETRIEVED。
- AC-T4：估算的移動時間標「估算，非導航」。
- AC-T5：給出 READY_TO_GO／NEEDS_FINAL_CHECK／DO_NOT_EXECUTE 判定、原因與核驗時間。
- 實跑題：「10/31（六）14:00 從住家出發，用常用交通方式去兩個市區景點，18:00 前回到家」→ AC-T1～T5 全過。2026-10-26 實跑：兩地週六都營業到 21:00；單程估算約 36 分鐘；排完約 17:40 到家；天氣 NOT_RETRIEVED、其中一個景點本體未直接核實、移動時間為估算，判定 NEEDS_FINAL_CHECK。

## 5. 呈現
摘要卡 → 時間軸 → 重要節點 → 備案 → 現場速查卡（現在／下一步、導航、移動與抵達、停留、硬截止、主／備班次、最小備案）→ 摺疊的來源。需要流程表時一律用 6 欄（ADR-004，取代原件 16 欄 ProcessStep16）：步驟／交付物、負責人、前置依賴、驗收條件、證據位置、狀態與下一步。

## 6. 禁止
直線距離冒充導航時間；他日班表冒充當日；Google 星等冒充品質；沒取得 Google 資料卻標已核實；UNKNOWN 當 0、False 或通過；捏造班次、票價、營業時間；沒有返程仍標可執行；只換一餐卻整個重排。寵物只在明確同行時才啟動同行檢查，並重驗當日狀態。
