# miko-core 閉環規格：C1 至 C6

- 依據：D16，miko-core 為流程唯一權威，UCP 併入核心
- 對應：C1 至 C6 對應 UGA 製作流程 A08 至 A13
- 狀態：PROPOSED，未寫入正本、未生效；草案修訂 0.2

## 一、對應表

| UGA | 本文件 | 名稱 | 核心負責 |
|---|---|---|---|
| A08 | C1 | 自我驗收 | 逐條自檢、自我層標籤、證據檔 |
| A09 | C2 | 主動補強 | 可推導缺口補強、UNKNOWN 與 BLOCKED |
| A10 | C3 | 錯誤維護 | 最小單元修復、diff、帳本去重更新 |
| A11 | C4 | 有界重測 | 一輪定義、retest_round、上限三輪 |
| A12 | C5 | 獨立驗收 | L0～L3、驗收包、逐條判定、上限兩輪 |
| A13 | C6 | 交付收工 | MANIFEST、封裝雜湊、帳本快照、四態與聲明 |

## 二、條文

### C1 自我驗收

觸發：產出檔案、修改規則、跨平台寫入、或回報完成之前。

動作：依 AC 逐條自檢，每條寫判定與證據位置，AC 覆蓋率必須 100%；未執行的條目寫 `NOT_RUN` 並註明缺什麼；結果只能使用自我層標籤 `SELF_PASS`、`SELF_FAIL`、`NOT_RUN`；證據存 `evidence/<task_id>/self-acceptance-vN.json`，不放入驗收包。

禁止：不得把 `SELF_PASS` 寫成 `ACCEPTED`；不得把未跑寫成 `PASS`；不得省略任何一條 AC。

失敗出口：任一 `SELF_FAIL` 進 C2，不得直接交付。

### C2 主動補強

觸發：C1 有未通過項目，或使用者指出缺漏。

動作：每個缺口先判斷能否由既有來源或規格推導；可推導者直接補並記下來源，不可推導者標 `UNKNOWN` 並寫原因；缺授權標 `BLOCKED`。同一項目補強上限兩次，此上限為本文件新增，UGA A09 原本沒有。

禁止：不得憑空創造來源；不得為通過而放寬 AC；不得只寫待補。

失敗出口：同項目兩次仍不過，進 C3 並記錯誤帳。

### C3 錯誤維護

觸發：錯誤出現、C2 補強無效、或使用者回報問題。

動作：先定位最小受影響單元，可以是步驟、欄位、章節或帳本條目；只修該單元，重測只跑受影響的檢查與測題。只有三種情況才擴大：錯誤跨兩個以上步驟、錯誤改到契約或欄位定義、該單元沒有可單獨執行的檢查；擴大理由寫進變更紀錄。修完保存 diff，寫入錯誤帳與變更帳；帳本命中去重鍵時就地更新並保留前一版，不覆寫歷史；同類錯誤第二次才寫入錯誤帳。

禁止：不得全面重跑後宣稱已修；不得刪除失敗紀錄；不得在沒有 diff 時說已修正。

失敗出口：修不動或需改規則，標 `BLOCKED` 交 MIKO。

### C4 有界重測

觸發：C2 或 C3 之後。

動作：一輪等於對受影響 AC 全集完整重測一次，並加一題新題；回歸集要全跑；每輪更新 `retest_round`；重測上限三輪。

禁止：不得無限重試；不得用同一方法重跑同一題期待不同結果；不得隱藏重測次數。

失敗出口：三輪未過標 `RETEST_EXHAUSTED`，交 MIKO，不得降級為大致完成。

### C5 獨立驗收

觸發：C4 通過，且產物要交付或要宣稱完成。

動作：由非製作者執行，等級照 L0 至 L3 判定，並以可證明的最弱一環為準。L0 同 session 或曾接觸製作內容，只給自我層標籤；L1 同模型新 session 冷啟動、只讀驗收包；L2 不同模型冷啟動，雙方模型 ID 要對照；L3 人類驗收者，需驗收者識別、時間與簽核紀錄。驗收者中途接觸作者說明、自我驗收結論或實作思路，降為 L0 並換人重驗，該輪計入 `audit_round`。驗收包要含產物、`packet-meta`、`ac/ac-table`、`results`、`MANIFEST`，並依逐條判定欄位寫 PASS、FAIL、NOT_RUN 或 BLOCKED 與證據；`audit_round` 上限兩輪。

禁止：不得由製作者自任驗收者；不得以整體通過代替逐條判定；不得在驗收後放寬 AC；不得把 L2 寫成正本採用的最終簽核。

失敗出口：`AUDIT_FAIL` 回 C3 並 `audit_round+1`；兩輪 FAIL 或包內缺件、雜湊不符，標 `BLOCKED`，原報告作廢。

### C6 交付收工

觸發：C5 為 PASS。

動作：交付前重建並驗證 `MANIFEST.sha256`，確認封裝雜湊一致；帳本快照入包；收工寫任務四態（完成、完成但有疑慮、需要資料、卡住）、困難卡七欄、未驗證清單、未寫入或未生效聲明；交接寫存檔處、下一步、待決。

禁止：不得省略困難卡；不得把候選寫成已採用；不得在無證據時宣稱 Runtime 生效。

失敗出口：任一項缺，回 C5 或 C3，不得交付。

## 三、狀態與預算

| 狀態 | 意義 | 解除 |
|---|---|---|
| `SELF_FAIL` | 自我驗收未過 | 補強後重驗 |
| `AUDIT_FAIL` | 獨立驗收未過 | 修復後重驗 |
| `RETEST_EXHAUSTED` | 重測三輪未過 | MIKO 裁決 |
| `BLOCKED` | 需外部條件或授權 | 條件解除後重驗 |

| 項目 | 上限 | 超限 |
|---|---|---|
| `retest_round` | 3 | `RETEST_EXHAUSTED` |
| `audit_round` | 2 | `BLOCKED` |
| 同項目補強 | 2 | 進 C3，記錯誤帳 |

## 四、與 UGA 的介面

UGA 判斷閘門開或關，核心判斷內容過或不過；兩邊都不重複定義對方的判定標準。UGA 條文保留至核心寫入並通過 AC-CORE 驗收後才可刪減。

## 五、驗收條件

`AC-CORE-01` C1 至 C6 六條齊全，各有觸發、動作、禁止與失敗出口；`AC-CORE-02` 預算表與狀態字典一致；`AC-CORE-03` 驗收者不得為製作者，L3 為人類簽核；`AC-CORE-04` 超限一律 BLOCKED 或 RETEST_EXHAUSTED，不得降級；`AC-CORE-05` 與 UGA 介面只有狀態與閘門；`AC-CORE-06` 既有硬邊界未被刪改；`AC-CORE-07` 驗收包含 packet-meta、ac-table、results、MANIFEST。

## 六、測題

`RT-CORE-01` 缺一條 AC 的產物，預期 `SELF_FAIL` 進 C2。`RT-CORE-02` 補兩次仍失敗，預期進 C3 並寫錯誤帳。`RT-CORE-03` 重測三輪失敗，預期 `RETEST_EXHAUSTED` 且不得第四次。`RT-CORE-04` 製作者自任驗收者，預期被拒。`RT-CORE-05` 缺困難卡或帳本快照的交付，預期 C6 攔下。`RT-CORE-06` 驗收者中途讀了作者說明，預期降 L0 並換人。
