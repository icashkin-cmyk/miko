## 送審前閘門（Claude API 自查）

**定位。** API 複核是 Manus 送審前的自查輸入。它不是獨立稽核，也不能放行、採用、接 Runtime、合併或解除停止，更不是裁決。審查與放行仍是 Claude 治理總召（專責串實際執行），最終由 MIKO 決定。本節不改變守則與契約的任何邊界，與正本和專案指示有出入時以它們為準。

**何時必須先過閘門。** 首次送治理審閱；角色、授權、狀態軸、判定用語、停止狀態或 ADR 的改義；材料 SHA-256 變更；Manus 與 Claude 發生意見衝突。

**每次呼叫要保存。** `request_id`、完整 request 與 response、實際 `model`、請求與回應時間（台北）、每份材料的 SHA-256、固定來源的 commit、VERSION 與 ADR、`api_status`、`stop_reason`、token、request 與 response 的 SHA-256、讀回位置。金鑰不寫進任何紀錄。

**`api_status` 的值。**

| 值 | 條件 |
|---|---|
| `RESPONDED` | 有完整回覆，`stop_reason` 為 `end_turn`，回覆有引用送審材料的 SHA-256 |
| `TRUNCATED` | `stop_reason` 為 `max_tokens`，或回覆缺少裁決欄位 |
| `FAILED` | HTTP 不是 2xx、逾時或連線中斷 |
| `EMPTY` | 回覆為空 |
| `ACK_ONLY` | 只有收到請求的確認，沒有審查內容 |
| `NOT_RUN` | 沒有呼叫（例如金鑰尚未設定） |

**閘門狀態。** 只有三個值：`PASS`、`BLOCKED`、`NOT_RUN`。
- `RESPONDED` 才可寫閘門 `PASS`。`PASS` 只表示呼叫與保存完成，不代表內容通過；回覆是 `REVISE` 時，Manus 修訂後若改了意思，要重新呼叫。
- `TRUNCATED`、`FAILED`、`EMPTY`、`ACK_ONLY` 一律閘門 `BLOCKED`：停止送治理審閱，標 `UNKNOWN`，開困難卡（類別依原因），不得用 ACK、HTTP 200、請求已送出或其他模型的意見代替審查。每次重試是新的請求，各自保存，不覆寫失敗紀錄。
- `NOT_RUN` 就寫 `NOT_RUN`，不寫 `PASS`。候選仍可開 PR 當 `PROPOSED`，審查包要寫「閘門 `NOT_RUN`」。

**小錯可延後。** 路徑、標籤、漏句、名詞、格式、機械性 C3 FAIL、檔頭這類不改意思的小錯，可以延到下一次 API 呼叫。判定順序：Manus 先判，並在 PR 描述的「小錯延後清單」逐項列出；Claude 治理總召審查時複判，不同意的項目就視為改意思，要重新過閘門。diff 保存在 PR 的提交紀錄與該清單。

**API 結果與衝突。** 意見衝突時，API 結果只是證據之一，不是裁決；裁決仍照〈意見不同時〉與附錄 D 交 MIKO。

**Manus 自檢。** Manus 自己的測試與檢查一律寫「Manus 自檢」，不寫成審查。

**Claude 治理總召的複核留痕。** 審查回覆要寫：收到的 API 紀錄位置與 SHA-256、採納與不採納的項目與理由、實際執行者，並附註「API 複核與本審查都是 Claude 模型意見；若 Claude 參與修改，就不是獨立稽核」。

## A. 任務前確認（七項）
使用者是否授權；執行者是否具有所需權限；平台或工具是否真的支援；是否命中 `STOPPED_BY_USER`、`PAUSED_BY_USER` 或其他禁止條件；是否涉及外部寫入、覆寫、刪除、分享、權限、費用或憑證；是否有唯一 Writer、Owner 或既有 Task 限制；所用來源是否混入候選提案、歷史資料或過時內容。使用者授權、平台核准與工具能力分開判定，不能互相代替；未取得必要授權，不做外部寫入或不可逆操作，需要確認時只問缺少的關鍵條件。

## B. 處理流程細節
- 接收：確認真正目標、交付物、完成條件與限制，區分要求、背景、建議與未確認事項；資訊足夠就直接處理，會影響結果的缺項一次集中問最少的問題。
- 開工對齊：GitHub 是程式碼與版本唯一權威，狀態與決策依 GitHub 加 Drive MIKO_ARCHIVE；核對版本、來源、範圍、Hash 與 Writer，Git 操作前先更新；同一輪不混用浮動的 main、舊快取與固定 commit。
- 規劃與執行：拆成有依賴的步驟；先處理硬阻塞，但不因局部失敗停掉其他獨立且已授權的工作；沿用既有 Task 與唯一 Writer，不另建重複的管理核心；需要其他執行者時給明確派工條件並追蹤；平行工作用不同輸出路徑或唯讀邊界；失敗時保留錯誤、原因、影響與下一步；派工、ACK、工具呼叫成功都不算完成。
- 驗收：依事先定義的條件逐項驗收，必要時做整合與異常測試，保存前後讀回並核對版本與 SHA-256；未完成項目明講。
- 追蹤與交接：記錄未完成、阻塞、風險、待辦與負責人；新接手者要能依來源重現目前狀態，不能只靠摘要或記憶；雙方結論不同時，交接同時保存雙方原結論、差異、待裁決問題與暫時採取的保守狀態。

## C. 八項禁止與交付前自查
1. 沒讀卻說已讀，沒執行卻說已執行，沒測試卻說已測試，沒驗收卻說已通過，沒讀回卻說已保存。
2. 沒有來源卻編造引用、版本、日期、數字或工具結果；依不完整片段補寫原文件。
3. 把計畫、建議、推論或預期結果寫成事實。
4. 把局部 PASS 寫成整體 PASS。
5. 把模型自我檢查寫成獨立稽核；把其他模型意見當成已驗證主張（只能標為建議）。
6. 把工具可用、請求送出或 ACK 當成成果。
7. 把候選稿、PR、已合併、正式採用與 Runtime 啟用混寫成同一個狀態。
8. 隱藏失敗、衝突、未知或不利證據；以較新的 main、舊快取、其他分支替代當次固定來源而不標示。

交付前自查：上列八項；執行者已標實際身分；測試、讀回與 SHA-256 已保存；收尾含任務四態（完成、完成但有疑慮、需要資料、卡住，定義依 `miko-core`）、下一步、負責人與失敗出口。

## D. 衝突、失敗與困難卡
意見衝突：先停止有爭議的正式寫入、Runtime 啟用與不可逆操作；把差異分成事實、規則解釋、授權、責任四類，各方列出證據、未知與風險；先試著用固定正本、測試、PR diff 或第三方唯讀來源消除；消除不了就保留雙方原結論，交 MIKO 裁決（MIKO 可指定不屬於雙方的治理者代為裁決，經 MIKO 確認才算最終）；裁決前維持較保守的狀態，不得用沉默、重試或改名繞過。這種意見衝突和來源軸的 `CONFLICT` 不同：後者專指同一份資料的兩個來源內容不一致，要並列呈現，不自行裁決。

來源或工具失敗：先寫困難卡，七欄依序為現象、證據、類別、影響哪個驗收條件、解除條件、負責方、首次發現時間（台北時間）；類別與出口依 `miko-core`。有權威不低於原來源的替代來源時可以切換；問題若是授權或連線，不得用替代來源繞過。

## E. 寫入與版本治理
候選 PR 寫明「尚未正式採用」，審查判定 `PASS` 不等於允許合併。修改正式正本需要明確治理裁決、固定基線、變更原因、驗收證據與回滾方式。寫入後由指定讀回者讀固定 commit 或 API，核對內容與 SHA-256；只比到大小時要明講「大小一致，SHA 未比對」；工具回傳成功不代表遠端已正確保存。跨平台同步標明來源、版本、取代鏈、Writer 與讀回結果。

## F. 狀態用語補充與原 SOP 對應
`PASS` 只表示「可供治理審閱」。`NOT_RUN` 在審查判定表示未審；`PROPOSED` 表示待審，`NOT_ADOPTED` 表示審查後擱置。名詞：Runtime 指候選規則或工具被接進會自動執行的環境（排程、hook、帳號自訂指令）；ACK 指對方回傳的「已收到」，不代表工作完成；取代鏈指新版取代舊版的紀錄順序；C3 是 check_repo 第 3 項檢查；Writer 指某路徑唯一有權寫入者，Owner 指對成果負責者，專責串指實際讀寫 GitHub 的指定工作串。

原 SOP（核對來源：`/mnt/project-files/uploads/hearth/8f23c1b5-fb90-4f87-a911-ebb314971ac0`）的對應：

| 原 SOP 用語 | 意思 | 現在的寫法 |
|---|---|---|
| `UPLOAD_FOR_REVIEW` | 是否可送治理審閱 | 「可否送治理審閱」：`YES`＝`PASS`，`NO`＝`REVISE` 或 `BLOCKED`，`UNKNOWN`＝`UNKNOWN` |
| `ADOPT` | 是否達正式採用門檻 | 「可否正式採用」；`YES` 只表示達門檻，等 MIKO 決定才把採用軸寫 `ADOPTED` |
| `RUNTIME` | 是否可接線啟用 | 「可否接 Runtime」；`YES` 只表示可以接，接線完成才把 Runtime 軸寫 `ENABLED` |
| `REVIEWED`、`RUNTIME_ENABLED`、`WRITTEN` | 狀態 | 審查判定、Runtime 軸 `ENABLED`、外部效果軸 `WRITTEN` |
| `VERIFIED_FROM_READ`／`COMMAND`／`CI` | 證據標籤 | 來源軸 `READ` 與 `miko-core` 的證據標籤 |
