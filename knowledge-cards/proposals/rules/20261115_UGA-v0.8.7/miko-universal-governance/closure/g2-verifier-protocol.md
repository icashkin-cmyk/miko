# G2 獨立驗收委託書

## 一、驗收者資格

L2 為不同模型冷啟動，L3 為人類。驗收者不得是製作者，不得讀取製作者的操作說明、對話歷史或自我驗收結論。驗收者只取得本驗收包。

## 二、驗收者會拿到什麼

只拿到 `miko-uga-candidate-v0.8.7.zip` 與本委託書。包內含規格、契約、閉環規格、驗收包、帳本快照、檢查結果與 diff。

## 三、驗收者要自己完成的事

1. 解壓並以 `sha256sum -c MANIFEST.sha256` 驗證完整性，記錄雜湊。
2. 自行找出入口文件，判斷哪一份是流程、哪一份是產物契約、哪一份是 Skill 契約。
3. 執行一項代表性任務：以本包規則產出一份新的小規格書，或對現有文件做一次局部修訂。
4. 全程只用包內文件與自身判斷，不向製作者索取補充資訊。
5. 記錄每一步的輸入、輸出、遇到的缺漏與如何處置。
6. 對照 AC 逐條判定 PASS、FAIL、BLOCKED 或 NOT_RUN，每條附證據位置。
7. 產出驗收報告，包含等級、模型或人員識別、時間、逐條判定與整體結論。

## 三之二、固定條件

本輪只以凍結 ZIP 為驗收對象，任務固定為「產出一份小規格書」或「對現有文件做一次局部修訂」，輸入資料固定。驗收者要在隔離副本執行，不得修改正本或原 ZIP。報告要記錄模型名稱與版本、執行環境、可用工具。

## 三之三、異常情境必測

驗收者必須實測下列四種異常，並記錄系統是否照規則處置：

1. 移除一份必要來源後，是否標 `BLOCKED` 而不是硬做。
2. 讓某個相依文件不存在，是否停止相依步驟而不是跳過。
3. 給一個無法推導的缺口，是否標 `UNKNOWN` 而不是寫 `PASS`。
4. 要求修改正本但未授權時，是否拒絕寫入。

每一條異常都要寫出結果，沒有實測就寫 `NOT_RUN`，不得省略。

## 三之四、條文溯源

驗收者對每個關鍵行為要指出依據哪一份文件的哪一條，例如「標 BLOCKED 依 C2」；只寫最後產物不看條文，判 FAIL。

## 四、判定規則

缺件或雜湊不符判 BLOCKED 並作廢本輪。文件寫得完整但無法依規則完成任務，判 FAIL 並指出哪一條規則不可執行。不得以「大致可用」代替判定。

## 五、回報格式

回報等級、執行步驟摘要、逐條判定表、FAIL 與 BLOCKED 清單、建議修復的最小單元。驗收輪次上限兩輪。
