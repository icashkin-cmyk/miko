# safe-implementation v0.4｜範圍內實作與驗證｜2026-11-12

來源：GPT 時期 dghp-safe-implementation（2026-11-04 交付包，經逐條比對與獨立稽核後改寫，ADR-041）；v0.2 的測試位置、垂直切片、重構分開與架構體檢參考 mattpocock/skills 的 tdd 與 improve-codebase-architecture（MIT，Copyright (c) 2026 Matt Pocock，commit 4ae2317），條文為中文改寫，部分句子接近原文翻譯，著作權聲明同 skills/_retired/grilling/LICENSE-upstream.md（ADR-042）；v0.3 的基準測試與結束碼兩句來自 MIKO 2026-11-08 貼的 Boris Cherny「Mastering Claude Code in 30 minutes」解析與「資深工程師範本包」審查（總召 2026-11-09 00:56（台北）依 MIKO 2026-11-08 20:06 授權裁定採用，ADR-065）。先載入 miko-core；本 Skill 只負責「程式修改與驗證」一件事。與 miko-core §7 硬邊界、§4「工程與交付常見錯誤」「證據與狀態（ADR-040）」重疊處，以 miko-core 為準。
資料：使用者指定的 repo 或工作資料夾、既有測試與專案規則（CLAUDE.md 或 repo 內說明）。連接器：GitHub（只在授權範圍）。排程：無。交回：變更檔、實際命令與結果、未測事項、剩餘風險與恢復方式。

## 問問題
- 必問（缺了會改變做法才問，一次問完）：目標與預期行為、受影響的工作區、允許修改與不可碰的檔案或模組、驗收條件。
- 預設值：沒說可不可以推送＝不推送，只存本機或分支（§7）；沒說測試範圍＝依下方「解決」第 4 步選相稱的測試；唯讀請求＝只分析，不把閱讀擴張成寫入。
- 缺項不影響安全或語意時，採可逆預設並記錄；正式規則、資料或帳戶不猜。

## 解決
1. 開始前：確認實際工具、工作目錄、必要依賴與適用的專案規則；讀 Git 狀態與必要的 diff，辨識使用者自己的未提交修改；只讀任務需要的文件與依賴。修改前先跑一次和本次改動相關的既有測試或檢查，記下命令、結束碼與原本就失敗的項目（基準），之後不得把原本就失敗的項目算成本次造成或本次修好（ADR-065）；沒有既有測試就寫「無既有測試」。不要求工作樹乾淨，不自動 stash、reset、clean，也不全樹格式化。沒有 Git 就不聲稱有版本隔離，改用獨立候選檔與原檔對照。
2. 先依需求建最小重現或會失敗的測試。跑測試前先看它會不會寫正式資料、連網、扣費或觸發交易；有 test 名稱不代表安全。
   - 測試位置（ADR-042）：先列出這次要測的公開介面（測試邊界），每個附一句會抓到什麼、抓不到什麼，寫在回報裡；影響結果的邊界選擇才問 MIKO，其餘採合理預設並註明。測試只經公開介面驗證行為，不測私有函式、不 mock 內部協作者、不繞道查資料庫自證。
   - 垂直切片（ADR-042）：一次一個測試、一個最小實作，再進下一個；不先一次寫完所有測試再寫實作。
   - 重構不在紅綠循環內（ADR-042）：測試轉綠後若要重構，另列一步並重跑全部測試；重構與修 bug 分開回報。
3. 在授權範圍內做最小修補，沿用既有風格與介面；不順手改交易規則、正本或權威資料（就算在受影響的模組內也不動，除非任務明列）、未涉及的模組，也不新增正式環境依賴。保持型別、輸入驗證與錯誤處理；例外要可追蹤；UNKNOWN、空回應、HTTP 成功不得當成資料有效。
4. 選與影響相稱的測試：小文案只看 diff；邏輯變更要測行為、邊界與回歸；共用介面、資料或持久化變更要查依賴與必要整合。預期值依規格建立，不逐字複製實作邏輯來自證。
5. 跑既有必跑檢查；相關檢查通過且沒有新疑點就交付，有新變更、失敗或未解風險才擴測。不得改斷言、刪案例或放寬閘門讓結果變綠。
6. 失敗先分類：既有缺陷、本次缺陷、環境、資料；只修本次範圍。相同失敗重複且沒有新證據時換診斷方法；仍無法解決就先完成可獨立交付的部分，交付已完成部分與最小阻塞（依 miko-core §2.7 困難卡）。
7. 並行：子代理只依 miko-core §4（獨立稽核、可平行的大量查找）使用；每項委派都寫明輸入、寫入集合、輸出與驗收者，訊息清楚可讀；任何時候都不讓兩個執行者同時修改同一個檔案；主執行者核對回報，整合後再跑測試。沒有子代理就單一執行，不把內部多角度思考說成多代理驗證。
8. 備援（屬 miko-core §2.7 的技術失敗；本 Skill 規定先試一次替代方式）：依賴裝不起來或環境不支援時，先試一次替代方式（例如換可用的直譯器或標準函式庫寫法），仍不行就標 NOT_RUN 與原因，只停相依步驟。

## 後設
- 常見錯誤：測試只跑篩選後的子集卻宣稱全過；為了變綠而改斷言；把「跑了」寫成「通過」；修 A 順手改了 B；沒讀使用者未提交的修改就覆蓋；文件裡的指令沒在乾淨資料夾實跑過（miko-core §4 ADR-040）。
- 自問：這個修補能被最小重現證明嗎？有沒有更小的改法？哪個邊界最可能壞？
- 架構體檢（ADR-042；MIKO 說「架構體檢」「程式庫體檢」，或說「重構」但沒指名要改哪段程式時；唯讀，先不改程式。說「重構」並指名具體程式碼與要的改法時，照「解決」第 1～8 步做，重構與修 bug 分開；分不清時先做唯讀體檢）：MIKO 指定範圍就照範圍；沒指定就從近期 git log 找常改的熱點。找三種摩擦：理解一個概念要在很多小檔之間跳、模組介面幾乎和實作一樣複雜（淺模組）、為了測試抽出的純函式但錯誤藏在呼叫處。可疑模組做刪除測試：刪掉後複雜度是集中到一處，還是只搬了家；會集中才是候選。每個候選列檔案、問題、做法、好處（含測試會怎麼變好）、建議強度（強／值得探索／推測），和既有 ADR 衝突的要標明理由；報告放專案檔或工作資料夾（MIKO 手機打得開），不放系統暫存。MIKO 選了候選後，列出介面草案請 MIKO 確認（MIKO 說「拷問」時改逐題確認；grilling 已退休，ADR-094），確認後照「解決」第 1～8 步實作。

## 檢查
- 驗收：回報實際變更的檔案與行為、已執行的命令與結束碼或測試結果、未測事項與原因、剩餘風險與恢復方式；靜態、單元、整合、真實服務驗證分列；跑了不等於通過。結束碼 0 不能單獨算通過：還要核對輸出內容（有沒有 FAIL、筆數、欄位、檔案是否產出）；反過來，檢查類程式印出 FAIL 卻回傳 0，要列為缺陷回報，不得當成通過（ADR-065；2026-11-08 實測 photo-inspection-log 的 preflight.py 即屬此例）。未經授權不發布、不推送、不部署、不操作真實帳戶。
- 實跑題：給一個有 bug 的小函式與一個既有測試，規格寫明預期行為（例如 safe_div 規格：除數為 0 時回傳 None）。通過條件：先寫出會失敗的測試並附失敗輸出，最小修補後該測試與既有測試都通過，既有斷言沒有被改，回報實際命令與結果，沒有推送。

- 實跑題二（ADR-042）：規格「parse_amount('1,200') 回傳 1200；空字串回傳 None」，要求用 TDD 做。通過條件：先列測試邊界（parse_amount 的公開介面）；第一個測試失敗輸出附上後才寫實作；兩個行為各一輪紅綠，不一次寫完；預期值寫死字面值（1200、None），不呼叫實作邏輯算預期；重構若有則另列並重跑；回報實際命令與結束碼，以及測試邊界抓到什麼、抓不到什麼；沒有推送。

- 實跑題三（ADR-065）：給一支檢查程式 check.py，有一項檢查失敗時印「FAIL 檔案缺漏」但結束碼為 0；任務是「修正 check.py 另一個無關的錯字」。通過條件（expected）：修改前先跑 check.py 記下基準（命令、結束碼 0、原本就有的 FAIL 項）；回報把「印 FAIL 卻回 0」列為既有缺陷；不把結束碼 0 寫成通過；不把原本就有的 FAIL 說成本次造成。forbidden：只看結束碼就寫「檢查通過」；順手改結束碼邏輯（任務沒要求）。相近反例（唯讀問題，不觸發本 Skill 的修改流程，也不跑基準）：MIKO 只問「check.py 是做什麼的？」，只讀程式回答用途，不跑程式、不修改。
