## 0. 結論（先看這裡）

1. ChatGPT 的三個「必須先修」裡，兩個成立、一個不成立：
   - 成立：共用契約與 miko-core 現有規格重複（§2-a）；狀態應拆軸，且現有 FINAL_HANDOFF 已經有拆軸欄位（§2-b）。
   - 不成立：「C6／C9 固定樣本回歸違反回測暫停」。2026-11-09 MIKO 已在決策卡裁定這兩項不算，並寫進 README 暫緩列、check_repo、CHANGELOG 1.2.51（ADR-074）。ChatGPT 只引用 2026-11-04 的停止，沒讀到這個例外（§2-f）。
2. 但這不代表十份設計沒問題：設計 09 除了 C6／C9 之外，還要修改回測引擎的旗標互斥、PIT／OOS 閘門與 checkpoint，這超出 ADR-074 例外範圍，等於「提議續做回測工程」，建議從本輪移出（§2-f、§5）。
3. 基準已過時：十個 Skill 在 6db897b（1.2.58）到 main 之間，只有 grilling 變動（+4／−2 行），其餘九個一字未動；變動集中在 miko-core、check.yml、check_repo、flowlock 腳本。所以十份設計的行號大多仍可用，但引用 miko-core 的行號與版本（v1.59、1.2.58）已失效，批次 -1 要重新釘到 1.2.70。
4. 「批次 0 過度停用」多數是誤讀：十份設計的 P0 都寫「停正式高副作用路由、保留唯讀／離線」。真正的問題是另一個：停用路由要改 Skill 觸發或帳號卡，屬 MIKO 裁決事項，設計把它放在「先做」不恰當（§2-d）。

### b. 六種狀態應否拆軸：**部分採納**

- 設計的 `EvidenceState` 把 NOT_READ／NOT_RUN／UNKNOWN／CONFLICT／BLOCKED／PARTIAL／PASS 放同一欄，確實混了來源、執行、授權、範圍四個維度。ChatGPT 對。
- 但「新增正交軸」也不必：19 欄 FINAL_HANDOFF 已有 ATTEMPT_STATE、EXECUTION_STATE、PUBLICATION_STATE、READBACK_STATE、ACTIVE_WRITER_STATE、COMPLETION_SCOPE（`multi-agent-coordination-engine/SKILL.md:327`），指令狀態六層另在 `references/evidence-states.md`。ChatGPT 提的 SOURCE_STATE／EXECUTION_STATE／EVIDENCE_STATE／AUTHORIZATION_STATE／COMPLETION_SCOPE 大半已有對應欄；缺的只有「來源取得狀態」與「授權狀態」兩軸，可用現有 PREFLIGHT_STATE／USER_DECISION 承接【推論，未逐欄比對定義】。
- 設計給的聚合函式 `aggregate()` 有行為問題（本輪實跑，`python3 -I`）：`aggregate([], True)` 回「完成」（空證據被當成完成，違反「UNKNOWN 不等於通過」）；`PASS+NOT_RUN+PARTIAL` 回「需要資料」，`PASS+UNKNOWN` 回「完成但有疑慮」，其餘分支與 `SKILL.md:220` 四態定義是否逐項相符，需在批次 1 對照。函式也沒有 PAUSED_BY_USER 輸入，只靠文字說「更高優先」。
- 與任務四態的映射：任務四態維持 `SKILL.md:220` 的定義，內部狀態只能映射進去，不能新增第五態。

### c. 原子寫入／SHA-256 是否不應一體適用：**部分採納**

- 設計並沒有主張把本機 fsync 套到 Gmail：02-gmail-cleanup 與整合報告 §5.3 都寫「本機輸出原子寫入；外部結果另行讀回，不能混稱」、「不能宣稱 Gmail 遠端讀回成功」。ChatGPT 對這點有誤讀。
- 但有兩處確實過度：整合報告 §2.2 要求 manifest 一律用 SHA-256 釘住；tw-alert-check（08）與 label-foreign-text（04）的來源是動態官方網頁，沒有不可變版本。這兩個該改成「URL＋查閱時間＋發布／生效日期＋回應內容雜湊」，而不是 pin 到固定 SHA。miko-core 已有日期一行與來源日期規則（`references/research-and-dating.md`），應引用而非另立。
- 結論：採納 ChatGPT 的來源分型表（GitHub／本機檔／網頁／API／動態官方資料）；原子寫入限本機檔案產物（photo、vci、make-skill）。

### d. 批次 0 是否過度停用：**部分採納**

- 十份設計 P0 的實際文字：travel「只保留唯讀與離線候選」、gmail「唯讀盤點優先」、grilling「只留唯讀逐輪提問」、label「唯讀／草案降級」、vci「READ_ONLY_DEGRADED」、tw-alert-check「只保留唯讀逐來源狀態」。所以「一律停用」不屬實。
- 真問題：(1) 停用「路由」要改 Skill 觸發描述或 MIKO 的帳號卡，屬 MIKO 裁決（整合報告 §4.3 自己也列為「必須 MIKO 裁決」），卻排在最前面；(2) 05-make-skill 的 P0「停 push／Drive／帳號卡路由」會動到專案指示已授權的「治理更新可免問推送」與 Drive 只新增，等於改授權，需 MIKO 明說；(3) gmail-cleanup 現況已寫「只問或盤點時唯讀」（description），P0 要補的是批准契約，不是再停用。
- 建議：批次 0 改為「逐 Skill 風險路由核對」，只產出允許／唯讀／禁止矩陣，不改任何 Skill 觸發；要改觸發另提 MIKO。

### e. 依賴圖是否真有證據：**採納**

- 整合報告與十份設計沒有跨 Skill 施工順序；唯一的跨 Skill 依賴證據是文件引用：01-dghp-travel 的 S1 天氣步驟呼叫 tw-alert-check（`fix_designs/01-dghp-travel.md:53`），travel 與 dghp-food 的餐飲節點交接（原 Skill 描述）。其餘（grilling→multi-agent、photo→make-skill、vci→任何）沒有程式或文件引用證據【推論：目前無證據，不是證明無依賴】。
- make-skill 的 skill_lint 是全 Skill 共用檢查工具（CI `check.yml` 有 test_skill_lint），這是工具依賴，不是施工先後依賴。
- 另有「writer」約束（專案指示單一 writer 表）：photo-inspection-log 由照片專案修，tw-backtest-workflow 由 DGHP 臺股專案修，總召只審查放行；travel、gmail、tw-alert-check、label 由總召代管；其餘總召本人。這比類別排序更有決定性。

### f. 回測：C6／C9 與 PAUSED_BY_USER（硬性項，如實回報）

事實：
1. `README.md:69` 暫緩列：「…check_repo C6／C9 用 repo 內固定樣本檔跑回測引擎回歸檢查，不抓新資料、不做策略研究，不算違反本列，CI 與本機照跑；此例外只限這兩項，其他任何回測引擎執行…」（後文被截，原文以 repo 為準）。
2. `CHANGELOG.md` 1.2.51（ADR-074）：MIKO 2026-11-09 在決策卡選「不算，明文寫成例外」。`tests/check_repo.py:87-88` 註解同。
3. 自動路徑確實存在：`.github/workflows/check.yml:36` 的 `python3 -I -B tests/check_repo.py` 沒帶 `--skip-backtest`，每次推送與每個 PR 都會執行 `bt_min.py`（C6 於 `tests/check_repo.py:144-146`，C9 同檔 197、245 行）。其他 workflow 步驟（test_terms、flowlock、skill_lint、unittest tests、vci、photo）沒有引用 `bt_min` 或 tw-backtest（`grep -ln "bt_min\|tw-backtest" tests/*.py` 只命中 check_repo.py）。
4. 本機：`--skip-backtest` 時 C6／C9 印 NOT_RUN，不算 PASS（`check_repo.py:65`）。屬「選項」，是否算回測：依 README 例外不算；ChatGPT 的「改名唯讀回歸仍是回測」是對的語意，但 MIKO 已對這兩項明文豁免。
5. 本輪沒有執行任何 bt_min、沒有抓市場資料；本輪 check_repo 以 `--skip-backtest` 跑（見 §7）。

判定：
- ChatGPT「C6／C9 違反 PAUSED_BY_USER」：**不採納**（已有 MIKO 明文例外，證據：README:69、CHANGELOG 1.2.51、check_repo.py:87-88）。我不擅自改這條，MIKO 若要推翻是新決定。
- 但設計 09 的範圍：整合報告 §3.9 寫「保留 C6／C9」符合例外；同節與 `09-tw-backtest-workflow.md` 還要改 `--events/--adjusted/--ignore-events` 互斥、manifest／PIT／OOS、checkpoint、樣本不足 hard gate，這些是修改回測引擎與流程，超出例外且 writer 不是總召。→ **部分採納 ChatGPT 的結論**：09 整份移出本輪修復清單，維持 PAUSED_BY_USER；不提議恢復。
- 現有 repo 是否還有其他自動跑回測的路徑：僅 check_repo C6／C9（經 CI 與本機預設）。`tests/CODEX_TEST_PLAN.md` 是歷史測試計畫，內含手動步驟，不會自動執行【已查：未被 workflow 引用】。
